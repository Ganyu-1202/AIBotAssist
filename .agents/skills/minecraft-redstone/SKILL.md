# 红石机器设计与诊断

这份 skill 面向本项目游戏内 agent，目标是按玩家需求制作能验证功能的机器。无需把需求限制成现成模板；模板不支持时，用 execute_task 的 plan 自定义布局。不要把 build_structure 当成红石机器生成器。

## 从功能到方块

1. 明确输入、输出、动作顺序、启动方式、停机方式及验收条件。已有机器先 inspect_machine / inspect_area，看现状和容器库存，避免整体拆除重建。调用 query_registry 核对当前版本方块状态。
2. 调用 observe_world 固定原点和世界轴。方案所有坐标相对该 origin，x 东、y 上、z 南；面向不改变坐标轴。各分支沿同一原点设计，特别检查最后一个中继器到负载之间的格子。
3. 用表格或短列表给出信号链：信号源 → 导线 → 中继器/比较器 → 负载；另列物料输入/输出和脉冲路径。计算每段线长、延时和供料间隔，再转成方块方案。
4. 优先复用 machine_blueprint：signal_test（拉杆→中继器→灯）、piston_test（拉杆→中继器→活塞）、repeater_clock、auto_smelter、auto_crafter。不能把模板静态检查通过当作机器已运行。
5. 自定义方案先 analyze_redstone_plan，再 preview_task；静态诊断只能发现部分几何问题，仍需核对现场现有方块、支撑和实际红石传播。
6. 建造时先承重/绝缘层，再导线和元件，最后供料及启动。先让机器停机，保留可达的断电位置。不要为消除动态状态差异重复拆放有物品的机器。

## 本项目 Java 1.21.1 的关键规则

- 红石粉信号强度 0–15，沿粉线传播会逐格衰减。长线使用方向正确的中继器恢复至15；不得根据外观“靠近”假定已经连上。
- **Java 方块状态中，中继器和比较器的 facing 是输入侧，输出在相反侧**。例如信号要沿 +Z 传播，中继器属性应 facing=north；输入邻格 z-1，输出邻格 z+1。不要套用发射器/活塞的 facing 语义。query_registry 返回合法属性，inspect_machine 返回实际端口坐标。
- 中继器 delay=1..4，分别延迟2/4/6/8游戏tick（1红石刻=2游戏tick，正常20TPS时一游戏tick约0.05秒）。侧面中继器/比较器可锁定中继器；检查侧向输入，避免把锁定误判为断线。
- 比较器 compare 模式：后输入不小于两侧最大输入时输出后输入，否则0；subtract 模式输出 max(后输入−最大侧输入,0)。容器读数取决于占用率和物品堆叠上限，不是简单物品数量。不要把两侧输入相加。
- 红石粉、中继器和比较器需要合适支撑。上下台阶连线、透明/实心方块、强充能/弱充能规则不同；先用直线与明确端口工作，再压缩布局。不要用玻璃等不导电方块代替需要传导的实心方块。
- 发射器 facing 是喷射方向；投掷器和发射器不是同一种负载。持续高电平不等于连续发射；需要合适的关→开沿及恢复间隔。检查库存变化和实际喷射位置。
- 侦测器 facing 为观察面，红点在反面输出短脉冲。观察的是方块更新，不是“有物品经过就必然触发”；要验证所用设备真的产生更新。
- 活塞 facing 是伸出方向；需要为伸缩体积留空间。原版最多推动12格，但不可推动方块、方块实体、黏液/蜂蜜附着、负载方向会改变结果。Java准连接及更新顺序不能当成所有模组/版本的通用行为；依赖它时明确标注并实测，优先显式供电。
- 关闭状态建造环形时钟；短脉冲能在环中循环，持续输入可能把整环锁成常亮。两个delay=4中继器合计16游戏tick延时；启停与环路时序需要跨tick采样，不用单帧截图判断振荡。
- 漏斗 facing 是输出方向；上方吸取、侧面投料/下方出料、红石锁定各不相同。先检查目标设备可接受的槽和方向。熔炉顶面进原料、侧面进燃料、底面出成品，模组机器必须查询其描述。
- 合成器需要正确的配方格、disabled_slots、供料和上升沿；持续供电不会自动连续生产。通用 auto_crafter 仅适合模板允许的单原料配方。多原料产线先 query_recipes/query_jei，设计配比、过滤/分料、缓存和停机条件，不能把混合原料扔入一个漏斗就宣称可用。
- 电气/更新状态如 power、powered、locked、triggered、导线连接经运行会变化；只在确有需要时显式约束，不把运行时状态当成要反复修复的结构错误。

## TNT 与危险动作

玩家要求设计/建造并不自动要求试射。大炮先检查装药和弹丸支路独立性、水槽、发射器朝向、两路延时和末端连接，保持停机。必须有明确试射要求才点火；试射前清理玩家与结构风险区。没有运行证据就报告未试射，不保证射程或装药安全。普通无破坏性的灯/活塞测试可按用户制造需求验证。

## 完工和排错

- verify_result 检查结构，inspect_machine 检查端口、信号、库存；已授权启动后隔一段游戏时间再次取样，比较输入消耗、输出增量、活塞位置或灯状态。截图只验证外观，不能证明吞吐或红石时序。
- 失败时沿链逐段检查：源有无变化 → 粉线是否衰减到0 → 元件方向/锁定/延时 → 输出邻格是否接到负载 → 负载库存/空位/更新条件。修补局部后再测，不盲目重建。
- 报告区分“建造完成”“静态检查通过”“实际功能验证通过”。功能验收要写清观测到的变化；未测部分明确列出。
- 模组机器先 query_mod_operations，读取注册的参数、权限、副作用和 verification；run_mod_operation 仅调用已注册ID。未注册时参考 inspect_machine、command_help 和真实配方，不捏造模组API。操作返回 unknown 时停止并检查状态，不重新调用。

规则适用范围：Java 1.21.1。本项目 RedstoneDiagnostics / MachineBlueprints / SpecialPlacement 以及映射后的原版 DiodeBlock、RepeaterBlock、ComparatorBlock、ObserverBlock、PistonBaseBlock 是对应实现依据。模组改变规则时优先遵循实际注册描述和实测结果。
